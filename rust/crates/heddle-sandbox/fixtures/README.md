# The recorded approval question

A recorded one-question approval exchange, for the Web UI checks that judge the approval card without having to
arrange a live denial first. The files are a **sample**, not a second contract: a check compares the running
server's bytes with them, and `cargo test -p heddle-sandbox` fails if the crate's serialisation stops producing
them.

| File | What it is |
|---|---|
| [`approval-question.json`](approval-question.json) | one `ApprovalRequest`, compact, exactly as the wire carries it (camelCase; `session` is present because this recorded question belongs to a session) |
| [`approval-stream-frame.txt`](approval-stream-frame.txt) | the SSE frame that carries it, byte for byte: `event: approval` newline, `data: ` + the JSON, then a blank line |
| [`approval-answer-allowed-once.json`](approval-answer-allowed-once.json) | the body of the answer that grants exactly this call |
| [`approval-answer-rejected.json`](approval-answer-rejected.json) | the body of the answer that refuses it |

## The contract these files record

The page (`src/server/page.html`, `showApproval` and `answerApproval`) and the service
(`src/approvals/service.ts`, `ApprovalService::request`) agree on four things, and these files carry all four:

1. The stream event is named **`approval`**; the page subscribes with `events.addEventListener('approval', …)`.
   Any other event name leaves the card hidden.
2. The frame is `event: approval\n` then `data: <the request's JSON>\n\n`. The blank line ends the frame; the
   `data:` line holds the compact JSON, not a pretty-printed object.
3. The request's fields are `id`, `tool`, `reason`, `displayReason`, `session` (omitted when the question has no
   session) and `at`. The page draws `displayReason ?? reason`, filters on `session` when it draws a card for its
   own session, and uses `id` to answer. A `sandbox_permissions: "danger-full-access"` escalation reads
   `Allow this command with danger-full-access permissions: <the model's justification>`, which is what makes the
   card's text matched by the permission and Web UI checks.
4. The answer is `POST /api/approvals/<id>` with `{"outcome":"allowed-once"}` or `{"outcome":"rejected"}`. A
   success is `200` with `{"answered":true}`; a question no longer waiting is `409` with `answered: false` and an
   `error`, and the page keeps its card up in that case.

## How a check consumes it

From the repository root, the files are at
`rust/crates/heddle-sandbox/fixtures/` (`approval-stream-frame.txt` and the rest). Two uses, both cheap:

- **The frame is the oracle, in two parts.** Split the live frame and `approval-stream-frame.txt` the same way:
  the **envelope** (`event: approval\n`, then `data: `, then one line, then `\n\n`) must match byte for byte,
  and the **payload** on the `data:` line must equal the recorded object as parsed JSON (deep equality) once the
  recorded `id`, `session` and `at` are replaced with the live question's (from `GET /api/approvals`, or from
  the frame itself). A renamed field, a pretty-printed payload (it spans more than one line), a missing blank
  line, a wrong event name or a dropped `displayReason` all fail one part or the other.
- **The answers are the requests.** Post `approval-answer-allowed-once.json` (or the rejected one, or a literal
  with the same bytes) to `/api/approvals/<live id>` and expect `200 {"answered":true}`; post the same body again
  and expect `409`, because a question settles once.

**Key order is not part of the contract, so do not compare the payload as text.** The page reads the payload
with `JSON.parse`, which ignores key order. The recorded file has the TypeScript build's insertion order (`id`,
`tool`, `reason`, `displayReason`, `session`, `at`), and the Rust crate's own `ApprovalRequest` serialiser writes
the same order. But a server that forwards the question through `serde_json::Value` keeps that order only when
serde_json's `preserve_order` feature is on. In this workspace it is on only through feature unification:
`heddle-llm` enables it. Without it the keys would come out sorted. That run would be correct, yet a text
comparison would fail it.

## Provenance

Recorded by hand on 2026-10-22 from the two sources named above at `origin/main` `1bcff7e`, not generated by a
TypeScript build: the `ApprovalRequest` field list and the display-reason wording come from
`src/approvals/service.ts`, and the frame and answer shapes from `src/server/page.html`. The crate's tests
(`rust/crates/heddle-sandbox/src/fixture.rs`) pin its own serialiser to these bytes, so a change on either side of
the seam fails there first, without needing node, a browser or a running server.

**The identifiers are canonical placeholders, not ids from any run.** The question's `id` is
`approval-00000000-0000-4000-8000-000000000002` and its `session` is
`session-00000000-0000-4000-8000-000000000001`. Both keep the real shape (a v4 UUID, so the version and variant
nibbles are `4` and `8`), and every other digit is `0` apart from the last. That is the placeholder shape the
repository's public-hygiene gate exempts: no generated UUID looks like this, so a real session id cannot hide
behind it. The `at` timestamp is likewise fixed text. A check replaces all three with the live values before
comparing, as described above.
